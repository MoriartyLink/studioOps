# StudioOps

StudioOps is a lean internal operating system for a 2–10 person creative or software studio: projects, tasks, project-based payments, and monthly operational reports.

## Setup

```bash
npm install
cp .env.example .env.local
npm run dev
```

Create a Supabase project, then add `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY` to `.env.local`.

Apply `supabase/migrations/0001_studioops.sql` in the Supabase SQL editor or with the Supabase CLI. The migration creates tables, indexes, RLS policies, status types, payment total synchronization, and profile creation trigger.

Create the first Auth user (email/password) in Supabase Auth, then run:

```sql
update public.profiles set role = 'owner', full_name = 'Min' where email = 'your-owner@email.com';
```

Owners can then create member accounts from **Team → Add member**. This action needs `SUPABASE_SERVICE_ROLE_KEY` on the server only. Never prefix it with `NEXT_PUBLIC_` and never expose it to the browser.

## Local development

```bash
npm run dev
npm run build
```

Use Supabase email/password auth. Public registration is intentionally absent. The `supabase/seed.sql` file documents a safe starting point for development data; create Auth users first so profiles are generated by the trigger.

## Roles and security

- Owners have full studio access.
- Members can only see their project memberships, project tasks, own payments, and own payment transactions.
- Members may update only the status of tasks assigned to them. A database trigger prevents field changes even if a client bypasses the UI.
- Other members’ KPay data and private payments are protected by RLS.
- Payments become read-only in amount once paid; reopening and adjustment history should be recorded through the owner payment workflow.

## Deployment

Deploy to Vercel or another Node-capable Next.js host. Configure the same environment variables there, apply Supabase migrations before release, and ensure the production Supabase Auth URL configuration includes the deployed domain.
